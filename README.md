# bugDan

Исправление багов из TFS с помощью Claude: `bug_fixer.fix_bug` читает карточку, создает ветку от нужной
базовой, просит Claude внести исправление, пушит ветку, создает pull request
и добавляет в карточку комментарий «Исправление бага: <ссылка на pull request>».

Если Claude решил, что исправление в коде не требуется (проблема в данных, настройках или окружении, поведение
соответствует замыслу, баг уже исправлен), он не меняет файлы. Тогда ветка и pull request не создаются,
а в карточку добавляется комментарий «Исправление в коде не требуется» с объяснением Claude.

User Story и Task обрабатываются так же, но Claude получает другую постановку: изучить задачу из описания
work item и выполнить ее (константы `TASK_BLOCK`, `WORK_TASK`, `TASK_SLUG_PROMPT` в `bug_fixer.py`; для багов -
`BUG_BLOCK`, `FIX_TASK`, `SLUG_PROMPT`). Комментарии в карточку для них - «Доработка по задаче: <ссылка>»
и «Изменения в коде не требуются».

В конце ответа Claude оценивает, с какой точностью он устранил баг или решил задачу (строка
«Точность: N% - обоснование», `ACCURACY_TASK`). Эта строка не попадает в описание коммита и pull request,
а дописывается в комментарий карточки после основного текста.

Вложения карточки (любые файлы размером до 2 МБ, константа `MAX_ATTACHMENT_SIZE` в `bug_fixer.py`) скачиваются
в папку `<репозиторий>-ai/<номер>-attachments` рядом с worktree. Claude получает к ней доступ (`--add-dir`)
и список файлов в запросе; вложения больше лимита или те, что не удалось скачать, перечисляются в запросе
с причиной. Папка удаляется вместе с worktree после завершения работы.

Если при взятии бага в работу карточка в столбце **TODO** доски своей команды (команда из Area, иначе
команда проекта по умолчанию), она переносится в **Development**; состояние карточки меняется на связанное
со столбцом в настройках доски. Ответственный за баг (Assigned To) добавляется в pull request обязательным
рецензентом. Ошибки переноса и добавления рецензента не прерывают исправление, а только пишутся в лог запуска.
Названия столбцов задаются константами `TODO_COLUMN`, `DEVELOPMENT_COLUMN` в `bug_fixer.py`.

## Запуск по тегам

`server.py` принимает события service hook TFS. Подписка в TFS присылает события только по карточкам
с тегом **AIFix** (фильтр подписки), а тег репозитория проверяет сервер. Теги репозиториев задаются
в `config.json` словарем «тег → репозиторий»: `repo` - путь до репозитория, `rule` - необязательный путь
до файла с правилом написания кода для Claude, `default_branch` - необязательная ветка по умолчанию:

```json
{
  "tfs_hosts": ["tfs.example.com"],
  "tags": {
    "Applied": {
      "repo": "D:\\Projects\\master\\RX",
      "rule": "rules\\rx.md",
      "default_branch": "develop"
    },
    "Services": {
      "repo": "D:\\Projects\\master\\SmartInstruments"
    }
  }
}
```

`tfs_hosts` - обязательный список хостов TFS (без схемы, порта и пути), на которые сервер отправляет запросы
REST API с учетными данными (PAT или Windows-аутентификация). В нем должны быть хосты карточек и хосты remote
`origin` всех репозиториев. Ссылки на другие хосты не загружаются: события с такой карточкой пропускаются,
а ссылки на pull request и карточки из комментариев и описания - с предупреждением в логе. Иначе любой,
кто может написать комментарий в карточке, получил бы PAT или NTLM-ответ учетной записи сервера, оставив
ссылку на свой сервер.

Текст файла правила (UTF-8) добавляется в запрос к Claude как правила, которые нужно соблюдать при исправлении
в этом репозитории. Относительный путь считается от папки `config.json`. Если `rule` не задан (или пустой),
правило не применяется. Файл проверяется при запуске сервера и перечитывается при каждом исправлении,
поэтому его правки применяются без перезапуска.

Базовая ветка, от которой создается ветка исправления, ищется по порядку: в секции Development самой карточки,
в ее комментариях («ветка: vega/43383», «branch vega/43383»), затем так же в ближайшей родительской User Story
или Feature. Учитываются только ветки, которые есть на сервере. Если ничего не найдено, при запуске по тегу AIFix
берется `default_branch` репозитория из `config.json`, и в текст бага для Claude дописывается, что ветка взята
из значения «По умолчанию» для репозитория. Если `default_branch` не задан, работа не начинается: в карточку
добавляется комментарий о том, как указать ветку (секция Development, комментарий «ветка: <имя>» в карточке или
в родительской User Story/Feature) и что после этого нужно заново поставить тег AIFix. При запуске по AICheck (перенос в TODO)
исправление в этом случае не выполняется: в логе запуска и логе сервера пишется, что оно пропущено, т.к. ветка не указана.

Исправление запускается, когда на карточке с типом Bug, User Story или Task оказываются AIFix и тег репозитория,
в любом порядке:
запуск происходит в том изменении, где ставится второй из них, и идет в репозитории этого тега. Если в одном
изменении появилось несколько тегов репозиториев, исправление запускается в каждом из них. Пока стоит только
один из двух тегов, обработка не запускается. Правки других тегов, когда оба тега уже стоят, удаление тегов
и изменения карточки без правки тегов обработку не запускают. После завершения обработки (успешной или нет) сервер
снимает с карточки тег AIFix (если исправление запущено в нескольких репозиториях - после последнего из них;
ошибка снятия пишется в лог сервера). Чтобы запустить обработку повторно, AIFix ставят снова. При запуске
по AICheck (перенос в TODO) тег AIFix не снимается.

При запуске по AIFix в начале работы в карточку добавляется комментарий «[Bugdan]: Исправление запущено по тегу
AIFix (репозиторий <тег>)». Итоги дописываются в этот же комментарий: ссылка на pull request, объяснение Claude,
почему изменения в коде не нужны, подсказка, как указать ветку, или текст ошибки («Ошибка: ...», до 2000 символов,
полностью - в логе запуска). Комментарий создается и правится через новый API комментариев TFS
(`EDIT_COMMENTS_API_VERSION` в `tfs.py`); если создать его не удалось, итоги добавляются отдельными комментариями,
как при запуске по AICheck. Теги не различают регистр. Если AIFix и тег репозитория поставлены на карточку
другого типа, исправление не запускается, а в лог сервера пишется предупреждение о неподдерживаемом типе Work Item.
Запуски идут по очереди, по одному; лог каждого запуска пишется в `logs/fix_logs/<номер>-<тег>-<время>.log`,
общий лог сервера - в `logs/server/<ГГГГ-ММ-ДД>.log`, по файлу на каждый день. Каждая строка логов
начинается с даты и времени.

### Запуск сервера

```
set TFS_PAT=<PAT с правами Work Items (read & write) и Code (read & write)>
set BUGDAN_HOOK_USER=tfs
set BUGDAN_HOOK_PASSWORD=<пароль для вебхука>
python server.py
```

Сервер вызывает `bug_fixer.fix_bug(<ссылка на карточку>, <путь до репозитория тега>)`. Ссылка на карточку имеет вид `.../_workitems/edit/<номер>`. Префикс ветки берется из Area
карточки - уровень сразу под проектом (`SmartInstruments\Vega` → `vega/...`). Если Area - корень проекта,
префикс берется из базовой ветки (`vega/43375-x` → `vega/...`), а для `master` - `bugfix/`.

Параметры сервера: `--config` (путь до конфига, по умолчанию `config.json` рядом с `server.py`; конфиг
и пути в нем проверяются при запуске), `--verbose` (писать в лог и пропущенные события).
Модели задаются константами `MODEL` и `SLUG_MODEL` в `bug_fixer.py` или аргументами `--model`, `--slug-model` (и `--model-url` для своей модели, см. ниже). Адрес и порт (`0.0.0.0:8080`), путь вебхука (`/propose-fix`), типы карточек для AIFix (`Bug`, `User Story`, `Task`)
и для AICheck (`Bug`) и папка логов задаются константами `HOST`, `PORT`, `HOOK_PATH`, `FIX_TYPES`, `CHECK_TYPES`, `LOG_DIR` в начале `server.py`.
Проверка работы: `GET http://<хост>:8080/health`.

Для постоянной работы сервер удобно оформить службой Windows, например через NSSM. Служба должна работать
от учетной записи, у которой в PATH есть `claude` (или задан `CLAUDE_BIN` - абсолютный путь, лучше до `claude.exe`,
а не до обертки `claude.cmd`), выполнен вход в Claude
и настроен доступ git к репозиторию. Входящие подключения на порт сервера должны быть разрешены
в брандмауэре для сервера TFS.

### Подписка в TFS

Project Settings → Service hooks → Create subscription → **Web Hooks**:

- событие **Work item updated**, Area path `SmartInstruments\Vega`, тип карточки не задан
  (тип проверяет сервер), тег **AIFix**, поле **Tags**;
- URL: `http://<хост>:8080/propose-fix`;
- Basic authentication: `BUGDAN_HOOK_USER` / `BUGDAN_HOOK_PASSWORD`;
- Resource details to send: **All**.

Кнопка **Test** в мастере отправляет тестовое событие; сервер ответит `ignored`, это нормально.

## Проверки при переносе по доске

Endpoint `/check-work-item` принимает событие **Work item updated** для измененного поля **Board Column**
(отдельная подписка с теми же настройками, что и выше, но с полем Board Column и URL
`http://<хост>:8080/check-work-item`). Обработка идет только для карточек бага с тегом **AICheck**;
действие зависит от столбца, в который перенесли карточку (`board_checker.py`):

- **Analysis** - проверка описания бага (пока только запись в лог);
- **ReadyForDev** - проверка, что баг можно воспроизвести по описанию (поля описания карточки, `TEXT_FIELDS`
  в `tfs.py`). Оценивает Claude (модель `DESCRIPTION_MODEL`): понятны ли шаги, понятно ли, какой результат
  наблюдается и какой ожидается, и не противоречат ли они друг другу, понятно ли окружение - продукт (в том числе
  по тегам карточки) и, если это действительно нужно, ОС, версия и т.п. Версия берется и из поля карточки
  Found In Version (`FOUND_IN_VERSION_FIELD` в `tfs.py`) - в описании ее можно не повторять. Особых разделов
  или заголовков в описании не требуется, раздел «Пояснение» может быть пустым.

  Если описание ссылается на другие карточки (`.../_workitems/edit/<номер>` или ссылка на доску
  с `?workitem=<номер>`, в том числе упоминание карточки), Claude получает и описания первых `MAX_REFERENCES`
  из них: если баг аналогичен другой карточке (например, «требования аналогичные Bug 42301» для другого продукта),
  шаги и результаты в нем можно не повторять - достаточно, чтобы они были понятно расписаны в той карточке
  и было ясно, чем текущий баг от нее отличается. Карточка, которую не удалось загрузить, пропускается
  с предупреждением в логе.

  Если баг не воспроизвести по описанию, в карточку добавляется комментарий со списком проблем описания
  и упоминанием последнего, кто правил описание бага (по истории изменений полей описания; если его не найти -
  последнего ответственного), и ставится тег **AIWarning**. Если описание в порядке, тег снимается.
  Проверка идет в фоне, как для Ready for testing;
- **Ready for testing** - проверка, что в карточке есть информация о решении бага. Достаточно одного из:
  1. в разделе Development есть связанный pull request в работе или завершенный;
  2. в комментариях есть ссылка на такой pull request (`.../_git/<репозиторий>/pullrequest/<номер>`, ищется
     и в тексте, и в адресах ссылок).

     Pull request собираются и запрашиваются в TFS так же, как для Closed (см. ниже). Отмененные (Abandoned)
     pull request исправлением не считаются: если других нет, проверка продолжается, а в комментарий
     о недостающей информации добавляется список отмененных pull request;
  3. если pull request нет - в разделе Development есть связанный коммит (исправление могло быть слито
     коммитом без pull request);
  4. в комментариях есть ссылка на коммит (`.../_git/<репозиторий или его id>/commit/<sha>`);
  5. последний ответственный объяснил, почему баг не будет исправлен: в своем комментарии или дописав текст
     бага (по истории изменений полей описания). Последний ответственный - тот, кто последним был указан
     в Assigned To по истории карточки (на момент проверки поле может быть пустым). Есть ли в его записях
     такое объяснение, решает Claude (модель `DECISION_MODEL`); комментарии бота не учитываются.

  Если подтверждения нет, в карточку добавляется комментарий с упоминанием последнего ответственного
  (TFS отправит ему уведомление) и тем, чего не хватило: нет pull request или коммита, нет ссылки на них, и почему
  не подошли записи ответственного (не было записей, нет объяснения - с обоснованием Claude, или ответственный
  ни разу не был указан), а также ставится тег **AIWarning** (`WARNING_TAG`), по которому карточка выделяется
  на доске коралловым цветом (см. ниже). Если при следующей проверке подтверждение нашлось, тег снимается;
  если его не удалось поставить или снять, ошибка пишется в лог, а проверка продолжается. Итог проверки пишется в лог сервера. Проверка идет в фоне, по одной за раз;
  если запрос к TFS или Claude не удался, комментарий не добавляется, а ошибка пишется в лог;
- **Closed** - проверка закрытия бага. Собираются pull request карточки: связанные в разделе Development
  и по ссылкам из комментариев (повторы убираются; pull request по ссылке из комментария, который не удалось
  получить, пропускается с предупреждением в логе). Для каждого запрашивается состояние в TFS:
  - все pull request завершены (Completed; отмененные при этом не мешают) - проверка пройдена;
  - есть pull request в работе - карточка переносится из Closed в **Finalizing**, а в нее добавляется
    комментарий с упоминанием того, кто перенес карточку в Closed (по истории изменений столбца доски; если его
    не найти - последнего ответственного), и списком незавершенных pull request и их состояний.
    Если перенести не удалось, комментарий все равно добавляется и сообщает об этом;
  - pull request нет или все отменены - проверяются коммит (в разделе Development или ссылка в комментарии)
    и объяснение последнего ответственного, как для Ready for testing; если нет ни того, ни другого, карточка
    так же переносится в **Finalizing**, а в нее добавляется комментарий о недостающей информации (как для Ready
    for testing, с итогом переноса, но с упоминанием того, кто перенес карточку в Closed) и ставится тег AIWarning. В конце комментария подсказка: если баг закрыт
    правильно, можно снять с карточки теги AICheck и AIWarning и снова перенести ее в Closed - тогда она больше
    не проверяется;
- **TODO** - исправление бага, как при запуске по тегам, в репозиториях тегов, которые стоят на карточке.
  Если тега репозитория нет, исправление не запускается (предупреждение в логе сервера). Если ветка не указана
  ни в карточке, ни в ее родительской User Story/Feature, исправление пропускается (ветка по умолчанию не берется).

Перенос в другие столбцы пропускается. Названия столбцов задаются константами в `board_checker.py`
(`TODO_COLUMN` - в `bug_fixer.py`), сравниваются без учета регистра.

Проверки идут в фоне, по одной за раз. У каждой карточки в очереди ждет не больше одной проверки: если карточку
быстро двигают по доске, ждущая проверка заменяется проверкой для последнего переноса (уже идущая проверка
не прерывается). Перед запуском проверка загружает карточку и пропускается (с записью в лог), если карточка
уже не в том столбце, ради которого проверка была поставлена в очередь.

### Выделение карточек цветом

TFS не позволяет задать цвет отдельной карточке через API: цвет задается правилами стиля доски. Правило
настраивается один раз для доски каждой команды: Board settings -> **Styles** -> **+ Styling rule**:
- Name: `AIWarning`;
- Card color: коралловый `#D97757`;
- Criteria: **Tags** **Contains** `AIWarning`.

Можно также задать цвет самого тега: Board settings -> **Tag colors** -> `AIWarning`.

### Ограничения

- Срабатывает только изменение карточки. Если баг создан сразу с тегом AIFix и тегом репозитория (в том числе
  копированием), один из них нужно снять и поставить снова.
- Очередь хранится в памяти: события, пришедшие до перезапуска сервера и еще не обработанные, теряются.
- Если ветка бага уже есть, исправление завершится с ошибкой, ничего не изменив (видно в логе запуска).
  Чтобы все равно исправить баг заново, отправьте событие на `http://<хост>:8080/propose-fix?allow-duplicate=1`:
  будет создана еще одна ветка и еще один pull request. Если имя новой ветки совпадет с существующим,
  к нему добавится `-2`, `-3` и т.д. Параметр можно передать вручную (например, повторно отправив событие
  из истории service hook) или указать в URL отдельной подписки.

## Учетные записи и доступы

Приложение не хранит учетных данных: все доступы берутся из окружения той учетной записи Windows, от которой
запущен процесс (при работе службой - учетная запись службы).

- **Git-репозиторий.** Приложение вызывает обычный `git` (`fetch`, `ls-remote`, `push`) в папке репозитория из `config.json`
  и работает с remote `origin` этой рабочей копии. Логины и токены приложение git не передает: доступ берется
  из настроек git текущей учетной записи Windows - обычно из Git Credential Manager (сохраненные учетные данные
  или доменная Windows-аутентификация). Коммиты подписываются `user.name`/`user.email` из настроек git
  этой же учетной записи.
- **TFS (REST API).** Чтение карточки, поиск базовой ветки, создание pull request и комментарий в карточке идут
  через REST API TFS. Если задана переменная `TFS_PAT`, запросы выполняются от имени владельца этого PAT
  (нужны права Work Items и Code на чтение и запись). Если `TFS_PAT` не задана - под доменной учетной записью
  процесса через Windows-аутентификацию (пакет `requests-negotiate-sspi`). От этой учетной записи в TFS
  будут pull request и комментарий в карточке.
- **Claude.** Приложение запускает Claude Code CLI (`claude -p`, путь - из `CLAUDE_BIN` или из PATH). Доступ
  к Claude - тот, с которым авторизован CLI у текущей учетной записи Windows: вход, выполненный командой
  `claude` (`/login`, данные хранятся в `%USERPROFILE%\.claude`), либо ключ API из переменной
  `ANTHROPIC_API_KEY`, если она задана. Расход идет на аккаунт или ключ, под которым выполнен вход.
  Путь и версия CLI проверяются и пишутся в лог при запуске сервера. `TFS_PAT`, `BUGDAN_HOOK_USER`
  и `BUGDAN_HOOK_PASSWORD` в окружение `claude` не передаются. Если `claude` не завершился за `CLAUDE_TIMEOUT`
  (60 минут, константа в `bug_fixer.py`), процесс останавливается вместе с дочерними.

  **Своя модель.** Вместо Claude можно использовать свою модель (например, Qwen на сервере с vLLM), если сервер
  поддерживает для нее вызов инструментов (`tools` / `tool_calls`). Модель и адрес ее сервера задаются аргументами
  `server.py`: `--model-url` (адрес сервера с Anthropic Messages API `/v1/messages`), `--model-key` (его ключ),
  `--model` и при необходимости `--slug-model`. Сервер bugDan передает их только в окружение процесса `claude` (`ANTHROPIC_BASE_URL`,
  `ANTHROPIC_DEFAULT_*_MODEL` - чтобы служебные запросы Claude Code тоже шли в эту модель, и запрет обращений
  к сервисам Anthropic), а `claude` запускается с уровнем рассуждений `LOCAL_MODEL_EFFORT` (`medium`).

  `claude` работает только с Anthropic Messages API. Если у сервера модели есть только OpenAI API
  (`/v1/chat/completions`), на машине bugDan запускается прокси LiteLLM (в отдельном виртуальном окружении,
  у него много зависимостей). Его конфиг - копия `litellm.example.yaml` в `litellm.yaml` (не попадает в git)
  с адресом и ключом сервера модели и ключом самого прокси (`master_key`, без него LiteLLM не запускается).
  Конфиг должен быть только в ASCII: LiteLLM читает его в кодировке Windows по умолчанию:

  ```powershell
  python -m venv D:\litellm-venv
  D:\litellm-venv\Scripts\python.exe -m pip install "litellm[proxy]"
  D:\litellm-venv\Scripts\litellm.exe --config litellm.yaml --host 127.0.0.1 --port 4000
  .venv\Scripts\python.exe server.py --model-url http://127.0.0.1:4000 --model Qwen/Qwen3.8-27B --model-key <master_key>
  ```

  Прокси слушает только `127.0.0.1`. Стоимость в логе (`cost`) при этом считается по ценам Anthropic и не имеет смысла; токены и ходы - верные.
- **Вебхук.** Входящие запросы от TFS проверяются Basic-аутентификацией с логином и паролем
  из `BUGDAN_HOOK_USER` / `BUGDAN_HOOK_PASSWORD`; их же указывают в подписке service hook.
